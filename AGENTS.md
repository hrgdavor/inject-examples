## Shell Rules
- Platform: Windows PowerShell.
- Do NOT use `&&` in shell commands. Use separate tool calls or `;` instead.

## Where the contract lives

- [`doc/rfc/section-mapping.md`](./doc/rfc/section-mapping.md) — **RFC 1, section
  mapping**: the contract and the resolution core (status `0.9-rc`: the design
  questions are settled, 1.0 awaits exercise). What a mapper is and is not, the
  operations a port must expose, the two error categories, the **first line** a
  selection starts on, the band vocabulary, and the conformance obligations. Read
  it before writing or changing a port.
- [`doc/rfc/code-jump.md`](./doc/rfc/code-jump.md) — **RFC 2, code jump** (status
  `0.1-draft`), the navigation use case on top of RFC 1: what a cursor gets, the
  best-effort ladder an editor may climb, and why the same failure is a warning in
  an editor and an **error** in a gate. Normative only for policy; it never
  changes a resolve.
- [`doc/rfc/inject-examples.md`](./doc/rfc/inject-examples.md) — **RFC 3, inject
  examples** (status `0.1-draft`), this project's own use case on top of RFC 1:
  the document layer (markers, fences, rules), the strict gate, and what
  `--lenient` is and is not. Also policy only.
- [`doc/section-matching.md`](./doc/section-matching.md) — the normative
  resolution rules (how a reference resolves).
- [`test/vectors/manifest.json`](./test/vectors/manifest.json) — generated by
  `node tools/conformance-manifest.mjs`; the machine-readable map of the suite
  (every corpus, its row count, its row shape, what each field means, and which
  spec owns each layer). `npm test` gates it with `--check`, so it cannot drift
  from the corpora.
- RFC 1 is at `0.9-rc`: its design questions are settled, so a change that alters
  resolution, a message or the answer shape must update **both** its change log and
  the corpus, and the corpus row it moves is hand-checked, not trusted. A change to
  a **band** — when a failure is a warning and when it is an error — is a change to
  RFC 2 or RFC 3 (and to the rows that pin the band), never to RFC 1's resolution.
- The **profile corpus** is the one layer a port may skip:
  [`test/vectors/profile-vectors.json`](./test/vectors/profile-vectors.json),
  generated by `node tools/profile-vectors.mjs`, pins the jump policy of
  [RFC 2](./doc/rfc/code-jump.md) — the editor's landing line and `cause`, the band
  a gate refuses, and a whole document's failure list. It is separate from
  `section-vectors.json` on purpose: a profile is a product's policy, not the
  resolver's contract, so a port that implements the resolver alone does not read
  it ([RFC 1 §6.3](./doc/rfc/section-mapping.md)). Asserted by `lib/jump.test.mjs`
  and gated with `--check` by `npm test`, like every other corpus.
- **One separator, `/`, for every rule** — code, JSON, YAML, TOML and INI alike
  (`#scripts/test`, `#server/port`). A format's own spelling stays in the *output*
  (a TOML header is still `[a.b]`). `.` is never a reference separator.

## The demo pages (`docs/inject/index.html`, `docs/jump/index.html`)

- The pages are **generated** — never edit one by hand. **There are two demos**, and
  they are deliberately independent: neither menu lists the other and no page links
  across. One document, one page per language, twice over.
  - the **injection** demo (`docs/inject/index.html`, `docs/inject/languages/*.html`) is built
    from `docs/demo.md` and answers "what text does a reference put in my
    document?" — it is the `inject` page set;
  - the **navigation** demo (`docs/jump/index.html`, `docs/jump/languages/*.html`)
    is built from `docs/jump-demo.md` and answers "where does a reader land, and
    what happens when the exact block is gone?" — the `jump` page set, the
    [code jump](./doc/rfc/code-jump.md) use case. It is **not** the injection
    demo with different prose: a navigation document has **no fenced blocks at
    all** (a reference in it is a plain link, because a jump has nothing to put
    in the document), its pages have **no targets column and no description
    pane** (the document's own inline links are the navigation), and every
    target highlights **one line** — the line the reader lands on — rather than
    the span the reference covers (`landing` in the set).
  Both sets cover the same 19 slugs, so a language page exists on both sides.
  `tools/build-demo.mjs --pages inject --pages jump` builds both (`npm run demo`,
  `npm run demo:check`); `--pages <name>` alone builds one, and no `--pages` is the
  `inject` set, which is what every older invocation still means. A set is a record
  (`PAGE_SETS`), not the document's order, so one generator builds both.
- One document, one page per language. `docs/inject/index.html` is the **Overview** —
  the examples that are about the tool itself, whatever language the sample
  happens to be written in, closing with an index that links every language page
  — and `docs/inject/languages/<slug>.html` holds one language's or format's examples,
  so a reader can go straight to the language they came for. **The overview's own
  sections are targets like any page's**, not prose: a reader clicks its topics
  and the middle and right columns follow. A reference is written once in the
  document and shown on one page, so the Java sample's *direct* names are the
  overview's examples and its *path and line* forms are Java's page. **A marker is
  unique across a whole document**, so an example the overview shows is not
  repeated on a language page; a document is checked for that when it is
  generated, and the jump document is written from its own table.
- Every page has the **same header**, and in it the same hamburger menu: a
  `popover` (opened by the button's `popovertarget`, so light dismiss, Escape and
  the top layer come from the platform) positioned against the button with CSS
  anchor positioning (`anchor-name`/`position-anchor`/`position-area`, with a
  `@supports` fallback for browsers without it). The menu lists every page, marks
  the current one, and is how a reader crosses from one language to another. An
  entry is a **wrapping flex row**: the label bold on the left and, when it has one
  (`with-sample`), the file it reads (`samples/Cart.rs`) pushed to the right edge,
  so the file names scan down the menu as one column. **Only the Overview describes
  itself**, whose blurb takes a row of its own (`flex: 1 0 100%`), because a blurb
  under every entry turns the menu into a paragraph to read instead of a list to
  scan. The menu is `min(28rem, 82vw)` wide.
- **A target's id is per page** (`<slug>-t<section>-<target>`, and `t…` for the
  overview), because an id is an element id on one page while two pages may show
  the same reference.
- Three columns per page: the targets, the source file with the selected line
  range highlighted, and the document rendered GitHub-style (code fences
  highlighted) with the marker and its injected block highlighted in place. The
  first column is two stacked sections: the numbered titles with their example
  links only, and below them the description of the selected example — the prose
  written above its marker in `docs/demo.md` — which a click swaps in; the example
  link grows no snippet of its own. The lead — title and intro before the first
  `##` — is the Overview's banner, and is skipped in both the targets and the
  rendered column.
- Source: `docs/demo.md`. It is an ordinary Markdown document whose `##`
  sections become the numbered paragraphs of a page and whose markers become its
  clickable targets. Which page a section is published on is `PAGES` in
  `tools/build-demo.mjs`, which names the sections each page owns — the record,
  not the document's order, decides, so adding a section to a page is a one-line
  change there. **A section title is the key, so titles are globally unique**;
  each page's titles say what that language shows (`Java: regions and
  declarations`, `Go: a switch literal and a trailing comment`). The markers
  inject `docs/samples/*` — one sample per language and config format (Java,
  JavaScript, Go, Rust, Python, C#, Kotlin, PHP, Ruby, Shell, VB, Haskell, Zig,
  YAML, TOML, INI, JSON, CSS). A page's middle column has **no tab strip**: it shows
  one file at a time and names it in its own header (`Source file  samples/Cart.rs`),
  which the page script keeps in step as targets are selected.
- The pages are **grouped by feature**, not one section per example: a language
  page has two or three sections, and a section's examples share its prose (the
  description pane falls back to it). Where a language cannot show something —
  VB's `If x = "y" Then` header, Shell's `case` arms, Haskell's `case`, CSS's
  ambiguous `.card` — the page shows the nearest example that *does* resolve and
  says why in the prose; no page carries a fence the generator cannot verify.
- **An envelope** (`Inventory/^,toString,$`) is the answer to a member that reads
  as a fragment: the parent's declaration line, the member, and the parent's
  closing line, injected as three pieces with three ranges. `^` and `$` are whole
  path segments, the parent may be named on either end, and the marks **retry a
  name several blocks answer to** — which is what makes Rust's `Cart/^,add,$` name
  the `impl` that holds `add`. It is specified under
  [Envelopes](./doc/section-matching.md#envelopes) and recorded in the RFC change
  log. **Eight pages use it** (Java, JavaScript, Rust, Python, C#, Kotlin, PHP,
  Ruby, VB); the other four cannot, and say so: Go, Zig and Shell declare their
  members at the top level, and Haskell's `data Cart` has no body — a language gets
  an envelope section only where there is a declaration to wrap.
- Generator: `tools/build-demo.mjs`, run with Bun:
  `bun tools/build-demo.mjs --pages inject --pages jump` (or `npm run demo`) writes
  every page of both sets; `--check` (or `npm run demo:check`) exits 1 when one of
  them is stale. `tools/make-jump-doc.mjs` writes `docs/jump-demo.md` from its own
  table of references — a navigation document is a list of destinations, not a
  copy of the injection demo's examples — and it resolves every one of them while
  it writes, so the document cannot contain a link the tool would refuse to
  follow.
- Adding an example: put the sample in `docs/samples/`, write the `##` section
  with its prose and a marker in `docs/demo.md`, run `node cli.mjs docs/demo.md`
  to fill the block, add the section's title to the page that owns it in `PAGES`,
  add the page to the language index in `docs/demo.md` if it is new, then run the
  generator (a new file becomes another file the page's pane can show, named in the
  column header when a target reads it). Highlighting for every sample comes from
  the `HIGHLIGHTERS` table in `tools/build-demo.mjs`,
  whose comment/string spans are the resolver's own syntaxes; a new language needs
  a keyword set there too. For the navigation demo, add the reference to
  `tools/make-jump-doc.mjs`'s `SECTIONS` table and run it: the generator resolves
  the reference and writes the link, so a reference the tool cannot follow is
  caught before the page exists.
- `test.mjs` holds both sets to the docs' standard: `docs/demo.md` must be in
  sync with the samples and every target's line range must be the text it injects;
  `docs/jump-demo.md` must carry **no fenced block** and every reference in it must
  resolve; every section must be published on exactly one page; every page must
  carry the menu; each committed page must be byte-identical to the generator's
  output; and no page of one set may link into the other.

## Languages and the mask oracle

- `src/js/scanner/syntaxes.js` is the language table: **one object per
  language, all data** — comment spellings, string forms (`escape`, `hashes`,
  `maxSpan`/`content`, …), `heredoc`, plus the three optional extras the resolver
  consumes: `declarations` (the shapes the generic `name(` heuristics miss —
  Ruby `def`, Kotlin `fun`, Haskell bindings), `annotations` (what `+` brings
  along, e.g. a Haskell `name ::` signature), and a declaration's optional
  `suffix` (the trailing `!`, `?` or `=` Ruby allows after a bare name, which is
  part of the name and not a modifier). `src/js/scanner/tokenizer.js` walks the
  table; `src/js/scanner/lexers.js` maps extensions to it. `lib/section.mjs` must
  stay dependency-free and untouched by language detail.
- **A declaration shape's `headerFrom` is the end of its own match.** The resolver
  follows the header from there to the `{`, `;` or `=` that ends it, which is how
  a wrapped parameter list is spanned and how a Kotlin expression body is found.
  A shape whose match stops at the `(` therefore has to include the list, or say
  where it ends, and a shape for a language that writes `fun` must not also let the
  generic `name(` shape read an annotation's own arguments as a method.
- Adding a language: one object in `syntaxes.js`, one line in `EXTENSIONS` in
  `lexers.js`, a mask row in the lexical corpus (below), and probe entries in the
  oracle corpus.
- The corpus is `PROBES` in `tools/mask-oracle.mjs`; `test.mjs` runs it, so one
  entry is one test. `npm run oracle` cross-checks the same corpus against
  highlight.js (devDependency, never shipped): every region the highlighter
  calls a comment or string must be blank in our mask. `--emit` shows what it
  saw, `--self-test` proves the check can fail, `--no-oracle` needs no
  dependency.

## Examples in the docs

- A link whose text is **just a path** shows the reference it demonstrates: write the text as the path
  plus the fragment, so the syntax is visible in a preview and the link proves itself —
  `[samples/Inventory.java#catalog](./samples/Inventory.java#catalog)`.
- A **descriptive** link stays prose: `[the renderer](src/Cart.java#Cart/Line/render/-)` names what is
  behind it, and appending `#Cart/Line/render/-` to "the renderer" would be nonsense.
- A heading anchor into a document (`[Fences](#fences)`, `[§9](#9-decisions)`) is the descriptive case:
  the `#` is a heading slug, not a section reference.

## The lexical corpus

- `test/vectors/lexical-vectors.json` is generated by
  [`tools/lexical-vectors.mjs`](./tools/lexical-vectors.mjs) from the JavaScript
  implementation, and every port asserts it: `test.mjs`, `zig build test`,
  `mvn test`, `cargo test`. It carries two kinds of row, and both exist because
  the resolution vectors cannot cover them — their fixtures name only six of the
  eighteen lexer entries.
  - **`masks`** — one row per lexer entry (plus the built-in engine for an
    unknown type): a source and the mask it must produce. The mask invariant is
    asserted with it: same length, and every newline at its own offset.
  - **`shapes`** — one row per discriminating declaration spelling, asserting
    `declarations(maskedLine)` field by field (`kind`, `name`, `headerFrom`,
    `body`, `end`, `line`). The line is the **raw** line, not a masked one: the
    seam takes whatever it is given, and a spelling the resolver would mask away
    (a Haskell `add' x = 1`, whose `'` opens an unterminated char literal) still
    pins the matcher.
- The rows are chosen to *discriminate*: `impl<T: Clone> Display for Cart<T> {`
  beside `impl Cart {`, `publisher: String,` beside `pub name: String,`, an
  indented Haskell binding beside a column-0 one, a primed name beside a plain
  one. A row that would pass with either a right or a wrong matcher is not worth
  having.
- Regenerate with `node tools/lexical-vectors.mjs` (never edit the JSON by hand),
  then `node tools/zig-vectors.mjs` for the Zig copy. `npm test` runs both
  `--check` gates.

## The Zig port

- **Porting is allowed and the JavaScript implementation is the source of truth.**
  The goals, the gates and the rules for changing something after the port are in
  [`plans/zig-port.md`](./plans/zig-port.md) — read it before touching `src/`.
  The old freeze lives in `plans/section-matching/` and is history.
- `src/` mirrors the JavaScript file for file, and the port must produce the same
  bytes: `src/js.zig` (the UTF-16 code-unit runtime), `src/section.zig`
  (`lib/section.mjs`), `src/scanner/{syntaxes,tokenizer,lexers}.zig`
  (`src/js/scanner/`), `src/data_rules.zig` (the YAML/TOML/INI rules),
  `src/root.zig` (`index.mjs`), `src/main.zig` (`cli.mjs`).
- The Zig gates, all of which must be green: `npm test` (the JavaScript suite and
  both corpus drift gates), `zig build test` (which includes
  `src/section_vectors.zig`), `node tools/compare-zig.mjs` (JS vs Zig, byte for
  byte), and `zig fmt --check build.zig src`.
- The corpus in `test/vectors/section-vectors.json` gates the **shape layer**
  too, not only the grammar: property versus call versus statement, a body whose
  brace opens on the next line, an arrow expression, an anchor that is not the
  first thing in the braces, a region directive that is never an anchor. The rows
  whose expected answer is an *error* are the ones that catch an over-eager
  declaration matcher — a port can pass every resolution row while still
  over-matching, and those rows are where it fails. Assert every row; when adding
  one, pick an input that makes a wrong shape answer *differently*, not one that
  would pass either way.
- `src/section_vectors.zig` is **generated** — never edit it by hand.
  `node tools/zig-vectors.mjs` writes it from
  `test/vectors/section-vectors.json`, `test/vectors/lexical-vectors.json` and
  the fixture text; `--check` fails when it is stale. Regenerate it whenever
  either corpus changes or a fixture changes. It is `zig fmt`-clean, which is why
  every literal in it is written on one line: `zig fmt` joins a `"…" ++ "…"`
  chain, so a wrapped literal would make the generated file its own formatting
  failure.
- `zig build` and `zig build test` need a writable Zig cache; in a sandbox
  that blocks the global cache, pass
  `--global-cache-dir .zig-cache/global --cache-dir .zig-cache/local`.
- `.github/workflows/ci.yml` runs the JavaScript suite and oracle, the Zig build
  and tests, the differential harness, the Java port (`mvn test`), the Rust port
  (`cargo test`) and the formatting gates on every push and pull request;
  `.github/workflows/release.yml` builds the tagged binaries.

## The Java and Rust ports

- Two further ports of `lib/section.mjs` — the matcher module only, not the CLI —
  live beside it, for hosts that cannot import an ES module:
  [`java/section`](./java/section) (complete: `mvn test`) and
  [`rust/section`](./rust/section) (complete: `cargo test`). Both read the
  corpora **directly**, rather than keeping a generated copy, and both fail if a
  corpus row is unaccounted for. The real Maven binary is
  `D:\programs\mvn\bin\mvn.cmd`; `mvn` on PATH is the `mvnd` shim (see
  PUBLISHING.md).
- The JavaScript is the source of truth here too, so a disagreement is a bug in
  the port. `java/section/src/main/java/hr/hrg/inject/section/Syntaxes.java` and
  `rust/section/src/syntaxes.rs` are the tables; the Rust declaration matchers are
  hand-written in `rust/section/src/tokenizer.rs` (no regex engine, by design),
  which is exactly why the shape rows matter there.
- **Envelopes are ported everywhere.** `Inventory/^,toString,$` — the two marks, the
  head/tail piece, and the candidate retry that lets the member choose among a
  type's `impl` blocks ([Envelopes](./doc/section-matching.md#envelopes)) — is
  answered by the Java, Rust and Zig ports as well as the JavaScript, so the 31
  corpus rows carrying a `^` or `$` are rows every implementation passes. **Kotlin
  `fun` shapes** and the **indented condition/anchor** rows (`test/fixtures/Hash.py`)
  are ported too; all four implementations pass the whole section corpus.
- **One known port gap.** A Ruby name may end in `!`, `?` or `=` (`add!`, `empty?`,
  `add=`), and the JavaScript resolver reads such a segment as that name rather than
  as a name plus a modifier; the lexer reports the name without its suffix as `base`
  for that lookup. The Rust port reports the whole name and the same `headerFrom`, so
  the corpus rows it asserts are unchanged, but it has no `base`. **No corpus row
  exercises it** — `#add` and `#add!` both resolve the same way on today's fixtures —
  so the corpus does not catch it; a port that adds suffix support needs the lexer's
  `base` alongside `name`.
- **The ports' test harnesses must classify by the *row's* code, not the exception
  type.** An envelope whose marks contradict each other is thrown by the *parser*
  while carrying a `resolution/…` code, so `grammar/…` implies the grammar type but
  `resolution/…` implies nothing about it. A harness that asserts the reverse
  direction reports false failures (this bit the Java port's bucketing).
- The Java library has no runtime dependencies and no I/O; everything a caller
  needs is a `String` and a reference. `rust/section/src/tokenizer.rs` carries one
  hard rule worth knowing: every offset counts **UTF-16 code units**, as the
  JavaScript does, so a mask is over `Vec<u16>` and never over `char`s.
- **The differential harness needs the Zig binary at Medium integrity.** This
  workspace tree carries the sandbox's standing **Low mandatory-integrity label**,
  so a binary built into it cannot write to the Medium-labelled directories
  `tools/compare-zig.mjs` uses and every comparison fails with `EACCES`. Re-label
  after each `zig build`:
  `icacls zig-out\inject-examples.exe /grant "hrg:(F)"` then
  `icacls zig-out\inject-examples.exe /setintegritylevel Medium`. `zig build test`
  is unaffected (it writes only inside the workspace).

## Publishing

- Two routes ship from here: `npm publish` for the JavaScript package and the
  CLI, and Maven Central for the Java matcher in `java/section`. The Zig
  binaries ride a `v*` tag.
- The caveats that make a Maven release fail *quietly* — the `mvnd` shim that
  skips the publishing mojo, the Windows GPG pinentry stall, and the JDK
  difference between the two Mavens that decides which javadoc flags are legal —
  are in [`PUBLISHING.md`](./PUBLISHING.md). Read it before touching a POM's
  build section, and verify a release-shaped build with the real Maven binary
  rather than `mvn`.
